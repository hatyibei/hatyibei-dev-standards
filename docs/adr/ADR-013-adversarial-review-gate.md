# ADR-013: 承認前の敵対的レビューをフックで強制する

## ステータス
accepted

## コンテキスト

品質ゲート (lint / typecheck / test) を全て通した実装が、レビューで実害のある欠陥を指摘される事象が繰り返し起きている。

samurai-app PR #4070 (サブフロー機能) での実例:

| 欠陥 | ゲートの結果 | 発見者 |
|---|---|---|
| ワークスペース解約が FK 違反で失敗する | 3341 tests 全パス | Codex レビュー起点の調査 |
| アクセス制限された WF をサブフロー経由で実行できる | 全パス | Codex レビュー (P1) |
| 一度参照された WF が永久に削除できない | 全パス | ブラウザでの実操作 |
| 削除時に S3 のコード資産が残る | 全パス | Codex レビュー |
| backend と engine で入れ子深度の判定がズレる | 両方の全テストがパス | Codex レビュー |

いずれも「テストが足りなかった」のではない。**テストは実装者が置いた前提の中でしか書けない**ため、前提そのものが誤っている欠陥は、どれだけテストを厚くしても検出できない。

上記の例で言えば、実装者は一貫して

- 「削除は物理削除である」(実際は soft delete に変えたのは自分自身)
- 「候補一覧に認可は不要」(呼び出し元の認可しか見ていなかった)
- 「深度の境界は両者で揃っている」(callPath の初期値がズレていた)

という前提を持っており、その前提の上で正しいテストを書いていた。

**この欠陥が最も残りやすいのは、ユーザーに承認を求める直前**である。実装者は「ゲートが通った = 完成」と判断し、そこで検証を打ち切るため。

## 決定

**Stop フックで、承認を求める直前に敵対的レビューを強制する。**

`core/hooks/adversarial-review-gate.sh` を追加し、未共有の変更が閾値を超えている状態で敵対的レビューの記録が無ければ `exit 2` で停止をブロックする。stderr がモデルに返るため、モデル自身がレビューを実行してから応答を返すことになる。

### なぜ「フックで止める」なのか

ルールやスキルとして書くだけでは守られない。「ゲートが通ったので完成」という判断はモデルにとって自然であり、その判断が下される時点で自主的にレビューを挟む動機が無い。**判断の直前に機械的に割り込む**必要がある。

`block-no-verify` (`--no-verify` を禁止) と同じ位置づけで、自己申告に頼らない hard fail とする。

### 何をレビューさせるか

観点を分けて並行に走らせ、**別々の前提を持ったレビュアー**を当てる。1 つのレビュアーに全部を見せると、実装者と同じ前提に引きずられる。

- 認可 / テナント境界
- データ整合性 / 削除・トランザクション
- 実行系 / 並行性
- リリース安全性 / 既存機能の回帰

実行手段は subagent (Agent tool) と `codex-cli-review` skill の併用とする。前者は同一モデル内の視点分散、後者はクロスベンダーで前提の異なるレビューになるため、両方に価値がある。

**指示は「壊しにいけ」とすること。**「問題ないか確認して」と頼むと、レビュアーは実装者の前提を追認する方向に働く。

### 記録の仕組み

`tools/review/mark-adversarial-review.sh` が「その時点の変更内容のハッシュ」を `.git/adversarial-review.state` に書く。

ハッシュには未追跡ファイルの内容も含める。**レビュー後にコードを変えると記録は自動的に無効になり**、再度レビューが必要になる。「一度通せば以後素通り」を防ぐため。

### 発火条件

| 条件 | 挙動 |
|---|---|
| 未共有の変更が `ADVERSARIAL_REVIEW_MIN_FILES` (既定 5) 未満 | 素通り |
| `stop_hook_active` が true | 素通り (無限ループ防止) |
| git リポジトリ外 | 素通り |
| `CI` 環境変数あり | 素通り |
| `ADVERSARIAL_REVIEW_GATE=off` | 素通り (緊急時の逃げ道) |

小さな変更まで止めると形骸化するため閾値を設ける。逃げ道を用意するのは、塞ぐと迂回されて仕組みごと無効化されるため。

## 代替案

| 案 | 不採用理由 |
|---|---|
| A. ルール (`core/rules/`) に「承認前にレビューする」と書く | 守られない。上記の実例は全て「ゲートを通したので完成」という判断の後に見つかっている |
| B. `development-orchestrator` skill の手順に組み込む | skill を呼ばない経路 (小さな修正の積み重ね) で漏れる。実例の多くはその経路 |
| C. フックの中でレビュー自体を実行する | レビューは数分かかる。Stop フックの timeout に収まらず、また結果をモデルに解釈させる必要がある |
| D. PR 作成時の CI でレビューする | 遅すぎる。ユーザーが「これで良い」と判断した後に覆すことになり、手戻りが大きい |

C については、フックは**止めるだけ**にしてレビューの実行はモデルに任せる形にした。フックの責務を「判断の割り込み」に限定することで、レビュー手段 (subagent / Codex / 将来の別ツール) を差し替えられる。

## 結果

- 承認前に別視点のレビューが必ず 1 回入る
- レビュー後の変更は記録が無効になるため、直した後の再確認も強制される
- 閾値と逃げ道により、小さな変更や緊急時は従来どおり動く

**残る限界**: フックは「レビューしたか」しか見ておらず、レビューの質は問えない。形式的に走らせて記録するだけの迂回は可能である。ここは仕組みで担保できないため、ADR に意図を残すことで代替する。
